西邮点评家 微信小程序一期完整方案
版本：v1.0    日期：2026-09-29    定位：西安邮电大学校园食堂点评工具
技术栈：Java 21 + Spring Boot 3 + MyBatis-Plus + MySQL 8.0 + Redis 7
主体：个体工商户（已持营业执照）

================================================================
0. 项目定位与一期范围
================================================================
产品：面向西邮在校生的校园美食点评小程序，两个校区（长安校区、雁塔校区）。
一期只做"美食点评"单一核心功能（对象为校内食堂与校外美食区域），不做发帖、
不做图片上传，把内容安全与审核
机制做扎实，同时把用户体系、审核体系、风控体系独立封装，为二期（二手交易、
失物招领、拼单跑腿）、三期（树洞匿名、选课评价、校友内推）预留复用能力。

一期功能边界：
- 微信授权登录（wx.login + code2session），首次登录选择校区
- 浏览：校区 -> 美食地点（校内食堂 / 校外区域，如"东区校外""雁塔校外"）-> 档口/店铺 -> 菜品，查看平均分、评分分布、评论列表
- 综合排行榜：按近期评论热度输出最火菜品（7 天 / 30 天窗口）
- 点评：1-5 星打分 + 10-200 字文字评论，可删除自己的评论
- 对象可扩展：校区、地点、档口、菜品均支持管理端新增、修改、停用
- 内容安全：本地敏感词库 + 微信 security.msgSecCheck 双保险，审核日志 >=60 天
- 用户举报：举报违规评论，管理员 24 小时内处理
- 简易管理端：举报处理、违规下架、人工复审、敏感词管理、对象维护

2. 数据库表设计
================================================================
2.1 设计原则
- 模块化：所有可复用表（评论、内容、举报、审核日志）带 module / target_type 字段，
  一期点评、二期交易、三期树洞共用同一套表结构，不拆表、不重复造轮子。
- 用户、审核、风控独立成域：user / audit_log / report / sensitive_word 独立表，
  后续模块直接依赖，不做耦合修改。
- 预留字段：images JSON、module、audit_status、report_count、status 等字段
  一期就建好，二期启用零 DDL。
- openid / 手机号：密文（AES-256-GCM）+ 摘要（SHA-256 哈希做唯一索引）双列存储，
  可精确查询又不泄露明文。
- 评分聚合：dish 表冗余 avg_rating / rating_count，写时事务更新 + 读时 Redis 缓存。
- 逻辑删除：评论、内容统一 is_deleted 逻辑删除，保留审计痕迹。

-- 用户表（一期核心，二期手机号直接启用 phone 字段）

  `openid_hash`     CHAR(64)     NOT NULL COMMENT 'openid SHA-256 摘要，用于唯一查询',

  `status`          TINYINT UNSIGNED NOT NULL DEFAULT 1 COMMENT '1正常 0封禁',

2.4 数据流说明
- 评分聚合：评论通过审核后，在同一事务内 UPDATE dish SET
  avg_rating=(avg_rating*rating_count+新评分)/(rating_count+1), rating_count=rating_count+1；
  同时失效 Redis 缓存（DEL food:dish:{id}:stat），下次读取按需重算评分分布。
- 评论列表：走 idx_target 索引分页；热点菜品可叠加 Redis 列表缓存（一期可选做）。
- 删除评论：逻辑删除 is_deleted=1，同时回滚评分聚合（重算该菜品的均分与计数）。

3. 技术栈推荐
================================================================
3.1 前端
- 微信小程序原生开发（WXML / WXSS / JS），不引入重框架，减少审核与维护成本
- UI 组件库：Vant Weapp（可选，加快表单与列表开发）
- 请求封装：wx.request 统一封装 baseURL / token 注入 / 错误码拦截
- 路由：小程序原生页面路由 + tabBar（首页/菜品搜索/我的），板块按目录模块化：
    pages/
      auth/     登录、校区选择
      site/     地点列表（食堂/校外区域）、档口、菜品、评论、排行榜
      mine/     我的、我的评论、举报记录
      admin/    管理端页面（role=1 可见，或用独立管理 Web）

3.2 后端
- Java 21（LTS）+ Spring Boot 3.2.x
- MyBatis-Plus 3.5.x（单表 CRUD 免手写 SQL，参数化查询防注入）

- 腾讯云 Web 应用防火墙（WAF）基础版：CC 防护、黑白名单、人机验证
- 腾讯云 DDoS 高防（按需开通，攻击时再启用，按量计费）

- 微信云托管（CloudBase）：免服务器、自动扩缩容、自带 Redis/MySQL 生态，适合
  流量不稳定期；缺点是长链接与自定义网络能力受限，二期复杂交易建议切回方案A。

// utils/request.js 统一封装
const request = (method, path, data) => new Promise((resolve, reject) => {
  wx.request({
    url: 'https://api.xiyou-review.com/api/v1' + path,
    method, data,
    header: { Authorization: 'Bearer ' + wx.getStorageSync('token') || '' },
    success: (res) => {
      if (res.data.code === 0) resolve(res.data.data);
      else if (res.data.code === 10001 || res.data.code === 10002) {
        wx.removeStorageSync('token'); // 跳登录
        reject(new Error('未登录'));
      } else reject(new Error(res.data.msg));
    },
    fail: reject
  });
});
// 登录页
wx.login({
  success: (res) => {
    request('POST', '/auth/login', { code: res.code }).then((d) => {
      wx.setStorageSync('token', d.token);
      if (d.needCampus) wx.navigateTo({ url: '/pages/auth/campus' });
      else wx.switchTab({ url: '/pages/site/index' });
    });
  }
});

5. 违禁词处理流程（文字描述）
================================================================
入口：用户提交评论 POST /api/v1/reviews。

步骤一 基础校验（Controller 层）：
  登录态校验 -> rating 必须为 1-5 -> 正文 trim 后长度必须在 10-200 字之间 ->
  目标对象（菜品）必须存在且在售 -> 双层限流检查（用户 5 条/分钟、IP 20 次/分钟）。
  任一失败直接返回对应错误码，不进入审核链路。

步骤二 本地敏感词预检（Service 层，DFA 前缀树）：
  将正文按字符流进行 Trie 匹配，同时做归一化（全角转半角、小写化、
  去除零宽字符与分隔符变体）以命中变形词。
  - 命中 level=1（直接拦截类）词：立即返回 20003 友好提示，
    记 audit_log（check_type=1, result=0, hit_word），不调微信接口（省时省钱）。
  - 命中 level=2（需人工复审类）词：标记待复审，继续走微信审核。

步骤三 微信内容安全审核（security.msgSecCheck v2）：
  未命中本地词库（或命中复审类）时调用，参数：version=2、scene=2（评论）、
  openid=当前用户、content=正文、clientMsgId=预生成的评论 ID。
  三种结果：
  - pass：合规 -> 入库 audit_status=1，评论立即可见，异步刷新菜品评分。
  - risky：嫌疑 -> 入库 audit_status=3（人工复审），仅本人可见"审核中"提示，
    进入管理端复审队列，管理员 24 小时内确认通过或拦截。
  - revoke：违规 -> 入库 audit_status=2（拦截），对所有人不可见，
    返回友好提示（不用"违规"硬词，提示"内容需修改后重新提交"），记日志。
  微信接口异常（网络/额度）：降级策略——优先放行入库但标记 audit_status=3
  进人工复审（不阻塞正常用户），同时告警管理员排查。

步骤四 日志与留存：
  每次检查（本地或微信）都写 audit_log，含内容快照、命中词、风险等级、结果；
  日志保留 >=60 天；每日凌晨定时任务将超期日志归档至 COS 冷存并删除。

步骤五 举报闭环：
  用户举报 -> report 表（status=0 待处理）-> 管理员收到告警（IM/邮件/小程序通知）
  -> 24 小时内处理：block（下架评论 + audit_status=2）或 dismiss（驳回）；
  同一评论被举报 >=3 次自动置顶复审队列，>=10 次自动下架待人工确认（防刷）。

步骤六 词库反馈闭环：
  人工确认违规但词库未命中 -> 立即补词（sensitive_word 表，source=manual）；
  微信 revoke 高频特征词 -> 每周沉淀进本地词库（source=wx-feedback）；
  词库来源：开源合规词库 + 运营积累 + 微信反馈，启用前人工复核，避免误杀。

6. 安全防护方案（事前 / 事中 / 事后）
================================================================
6.1 事前预防（持续加固）
传输层：
- 全站 HTTPS + HSTS（preload），证书托管于 CDN/EdgeOne；
- 域名开启注册商锁定 + DNSSEC（服务商支持时），防域名被转出与解析篡改。
入口层：
- EdgeOne/CDN 前置：隐藏源站 IP（源站安全组只放行 CDN 回源 IP 段）；
- Web 应用防火墙（WAF）：开启 OWASP 核心规则（SQLi/XSS/命令注入）、
  自定义 CC 防护（单 IP 高频限速）、地域/UA 黑名单、人机验证（滑块）。
应用层：
- 参数化查询：MyBatis-Plus 全链路预编译占位符，杜绝拼接 SQL；
- 输入白名单：rating/枚举/字数/URL 协议严格校验；评论输出统一转义，
  小程序端不渲染富文本（纯文本 + text 组件），天然规避存储型 XSS；
- 双层限流：Redis + Lua 原子实现（用户维度、IP 维度），
  登录接口 5 次/分钟/IP，评论 5 条/分钟/用户，全局限流 20 次/分钟/IP；
- 登录态：token 存 Redis（TTL 7 天），服务端可随时吊销（封号即失效）；
  管理端接口校验 role + 管理 IP 白名单。
数据层：
- openid / 手机号：AES-256-GCM 加密（密钥存 KMS/环境变量，定期轮换），
  SHA-256 摘要做索引，任何日志不打印明文；
- MySQL：每日全量逻辑备份 + binlog 增量，备份上传 COS（异地），保留 30 天；
- Redis：设置 maxmemory 与持久化（AOF），仅内网可访问。
运维层：
- SSH 密钥登录、禁用密码；安全组最小开放（仅 443 对外，3306/6379 仅内网）；
- 依赖漏洞扫描（Trivy / 依赖检查）；微信 AppSecret 存环境变量/KMS，不入代码不入日志；
- 监控告警：CPU、带宽、入向流量、评论 QPS、审核失败率阈值告警。

6.2 事中应急（按场景触发，详见第 7 节手册）
- DDoS：切换腾讯云 DDoS 高防 / EdgeOne 原生防护，流量牵引清洗，隐藏源站；
- CC：WAF 限速 + 封禁攻击源 IP + 人机验证，必要时降级为队列/只读；
- 域名污染/劫持：更换解析、锁定域名、启用备用域名（提前备案的第二域名）；
- 接口刷量：Redis 风控定位 -> 临时封禁 token/用户 -> 复核清理 -> 收紧阈值。

6.3 事后恢复与复盘
- 日志分析：CLS/访问日志提取攻击特征（源 IP 段、UA、请求模式、时间窗、受影响接口）；
- 攻击溯源：向云厂商申请攻击流量报告/黑洞记录；DDoS/入侵可向属地公安网安报案
  （攻击他人系统属违法行为，平台方应保留证据）；
- 加固清单：按根因修复（验证码、参数签名、排队、扩容、词库补丁、封禁名单沉淀），
  修复后复测（压测 + 攻击模拟）再恢复全量；
- 复盘报告：时间线、影响范围、损失、改进项，沉淀进下一轮防护配置。

7. 抗攻击应急手册（分场景操作步骤）
================================================================
场景一：DDoS 攻击（域名被恶意流量打满）
触发信号：云监控入向带宽持续打满、正常用户访问超时/502、CDN 源站回源激增。
操作步骤：
 1) 确认：登录腾讯云控制台 -> 云监控 -> 带宽与入向流量曲线确认异常；对比源站
    CPU（若 CPU 正常而带宽打满，基本判定为流量型 DDoS）。
 2) 启用高防：开通腾讯云 DDoS 高防（或启用 EdgeOne 原生防护），将域名解析
    切换到高防 IP（A 记录），等待生效（TTL 短域名 60s 内）。
 3) 隐藏源站：源站 IP 改为仅允许高防回源（安全组放行高防回源网段，其余拒绝），
    对外彻底隐藏源站。
 4) 设置清洗策略：防护阈值按业务峰值设置（如 10Gbps / 500 万 pps 触发清洗），
    开启 TCP 连接防护与 UDP/ICMP 过滤。
 5) 封禁攻击源：WAF 对攻击 IP 段批量加黑名单（24-72h）。
 6) 若被黑洞（高防封停）：立即联系服务商紧急解封/更换高防 IP；启用备用域名
    （提前备案好的第二域名）+ 备用高防 IP 分流承载业务。
 7) 恢复验证：监控带宽回落、HTTPS 连通率恢复正常后逐步放开。
 8) 事后：保存流量报表与截图证据；必要时向公安网安报案（DDoS 属违法）；
    复盘后上调防护水位。

场景二：CC 攻击（接口频繁请求导致 CPU/数据库过载）
触发信号：QPS 异常升高、应用 CPU/数据库连接数打满、部分接口延迟暴涨。
操作步骤：
 1) 定位：CLS 查询访问日志，按接口、IP、UA 聚合出 TOP 攻击源与热点路径。
 2) WAF 处置：对目标路径配置限速（如单 IP 60 秒 30 次），对异常 IP 封禁；
    开启 WAF CC 防护模式（人机验证滑块）。
 3) 应用限流确认：核对 Redis 限流是否生效（rate:comment / rate:login 计数），
    必要时临时下调阈值（评论 3 条/分钟、全局限流 10 次/分钟）。
 4) 降级：若为评论/写接口被打，可切换异步队列（先写后审、排队落库），
    读接口走 Redis 缓存降级（列表/评分读缓存，DB 只读不写）。
 5) 扩容：轻量服务器临时升配（带宽/CPU），或挂负载均衡扩至 2 节点（需先改
    无状态部署，session 已在 Redis，天然支持）。
 6) 恢复与加固：攻击结束后更新 WAF 规则库、沉淀黑名单；优化慢查询与加缓存；
    压测复验后恢复原配置。

场景三：域名劫持 / DNS 污染（用户被解析到恶意服务器）
触发信号：用户反馈页面/接口异常、dig 结果与解析服务商控制台不一致、
SSL 证书报错（被解析到无证书的恶意 IP）。
操作步骤：
 1) 排查：本机 dig +norecurse 与 DNSPod 控制台对比解析记录；若解析值异常
    -> 判断劫持/污染；检查域名注册商状态（防被转出）。
 2) 处置解析：登录 DNSPod（或阿里云 DNS）核对并重置 A 记录，开启"域名锁定"，
    改强密码 + 开启两步验证；服务商支持时开启 DNSSEC。
 3) 启用备用域名：切换已备案的第二域名（修改小程序 request 合法域名 +
    服务器 Nginx server_name 多域名绑定 + SSL 多证书）。
 4) 防中间人：确认全站 HTTPS + HSTS 生效，提示用户通过官方入口访问
    （小程序端走合法域名白名单，天然避开污染 DNS 的网页入口）。
 5) 追责与加固：联系域名注册商核实转移/解锁状态；复盘 DNS 变更权限管理，
    避免弱口令/子账号滥用。
 说明：小程序端请求域名必须在公众平台配置合法域名白名单，因此小程序受
 DNS 污染影响较小；重点保护网页/管理后台入口。

场景四：接口被恶意刷量（脚本批量刷评论 / 刷分）
触发信号：评论写入速率异常、同一菜品短时间内大量同质评论、评分分布异常
（全 1 星或全 5 星）、新号集中发评。
操作步骤：
 1) 发现：监控评论 QPS 与单菜品评论速率；定时任务扫描异常分布并告警。
 2) 定位：按 openid / IP 聚合，锁定刷量账号集合（Redis 计数器辅助）。
 3) 处置：批量封禁（user.status=0 + 吊销 session token），其评论标记待复核。
 4) 数据修复：复核受影响评论，违规批量下架；对刷分菜品重算 avg_rating /
    rating_count（走回滚 SQL），删除被污染的统计缓存。
 5) 加固：保持评论 5 条/分钟限流；增加门槛（注册满 3 天或已完成校区选择才能
    评论，可选）；单菜品 1 小时新增评论 > 阈值时自动暂停新评论展示 + 告警。
 6) 沉淀：将刷量 openid/IP 加入黑名单（Redis 持久化名单），复盘后更新风控规则。

推荐服务商与产品（腾讯云为主，阿里云为备选）：
- 腾讯云：EdgeOne（CDN+安全）、Web 应用防火墙 WAF、DDoS 高防（BGP）、
  DNSPod（域名解析+DNS 防护）、轻量应用服务器、云监控、CLS 日志、COS、KMS
- 阿里云备选：DDoS 高防 IP、Web 应用防火墙、云解析 DNS（含 DNSSEC）
- 策略：DNS 解析优先 DNSPod（免费高防解析），高防按需开通按量计费，
  个人开发者不常驻高防以控成本，但必须保留一键切换脚本。

10. 补充：关于"代课 / 代写"等高危词的合规处理
================================================================
风险定性：代课、代写、代考等"学术不端服务"交易信息，违反校规并可能涉及
《普通高等学校学生管理规定》等要求，平台传播此类信息有合规风险，必须
零容忍。
处理措施：
1) 用户协议与隐私政策中明确写：
   "平台禁止发布任何形式的学术不端服务与违规交易信息（含代课、代写、
   代考、作业代做等表述），一经发现立即删除并封号，情节严重的将配合
   校方与监管部门处理。"
2) 敏感词库 category=5（学术不端）收录该类词及常见变形（空格分隔、符号
   插入、拼音缩写、同音字），归一化匹配；命中直接拦截（level=1）。
3) 举报分类增加"学术不端"选项，管理端优先处理此类工单。
4) 对外表述统一使用安全文案："平台不提供且禁止任何形式的学术代劳服务"，
   不在宣传材料中出现具体服务词。
5) 处理依据留痕：拦截/封禁均写 audit_log 与 user 备注，防止争议。

11. 降级方案（若一期审核门槛过高 / 类目被拒）
================================================================
方案 A（首选，纯工具化）：一期只做"美食信息查询"：校区、美食地点（校内
食堂 / 校外区域）、档口/店铺、菜品、营业时间、位置、价格展示；无登录、
无 UGC、无评论。
- 类目用【工具-信息查询】类（无需 UGC 资质，个体工商户可过）；
- 上线快、审核风险低，先积累用户与校园口碑；
- 点评功能留到资质齐备后以 v1.1 版本迭代上线（架构已预留，零重构）。
方案 B（半工具 + 轻 UGC）：只开放匿名星级评分（1-5 星，无文字评论），
评分做聚合统计展示；文字评论延后开放，审核面显著收窄。
方案 C（灰度验证）：体验版/测试版面向校内小范围内测，跑通审核链路与
体验后，再提交正式版代码审核，降低被驳回的返工成本。
建议路径：先 A 快速上线 -> 同步推进备案与类目 -> B 过渡 -> 正式版开放文字
点评（A 的页面与数据结构直接升级，用户数据无缝迁移）。

A1. 登录接口（Controller + Service）

@RestController
@RequestMapping("/api/v1/auth")
@RequiredArgsConstructor
public class AuthController {
    private final AuthService authService;
    private final RateLimiter rateLimiter;

    @PostMapping("/login")
    public R<LoginVO> login(@RequestBody @Valid LoginReq req, HttpServletRequest httpReq) {
        // 登录限流：5 次/分钟/IP
        rateLimiter.check("rate:login:" + clientIp(httpReq), 5, 60);
        return R.ok(authService.login(req.getCode()));
    }
}

@Service
public class AuthService {
    // code2session -> openid（AppSecret 从环境变量读取，不落日志）
    public LoginVO login(String code) {
        String openid = wechatClient.code2Session(code); // 内部：GET jscode2session
        String hash = DigestUtil.sha256Hex(openid);
        User user = userMapper.selectOne(
            new LambdaQueryWrapper<User>().eq(User::getOpenidHash, hash));
        if (user == null) {
            user = new User();
            user.setOpenidCipher(aesUtil.encrypt(openid)); // AES-256-GCM
            user.setOpenidHash(hash);
            userMapper.insert(user);
        }
        String token = IdUtil.fastSimpleUUID();
        stringRedisTemplate.opsForValue().set(
            "session:" + token, String.valueOf(user.getId()),
            Duration.ofDays(7)); // Redis session，可随时吊销
        return LoginVO.builder().token(token)
            .needCampus(user.getCampusId() == null)
            .user(UserVO.from(user)).build();
    }
}

A2. 评论限流（Redis Lua 原子实现，防止并发超限）

// RateLimiter.java
public void check(String key, int limit, int windowSeconds) {
    String lua = "local c=redis.call('incr',KEYS[1]) " +
                 "if c==1 then redis.call('expire',KEYS[1],ARGV[1]) end " +
                 "return c";
    Long count = stringRedisTemplate.execute(
        new DefaultRedisScript<>(lua, Long.class),
        List.of(key), String.valueOf(windowSeconds));
    if (count != null && count > limit) {
        throw new BizException(30001, "操作过于频繁，请稍后再试");
    }
}

A3. 敏感词过滤（DFA / Trie 前缀树，加载自 sensitive_word 表，Redis 缓存词库）

@Component
public class SensitiveWordFilter {
    private final TrieNode root = new TrieNode(); // 启动时从表加载，词库更新后重建

    public MatchResult match(String text) {
        String norm = normalize(text); // 全角转半角、去零宽字符、小写
        List<Hit> hits = new ArrayList<>();
        // 标准 DFA 遍历，返回命中的词与 level
        return MatchResult.of(hits);
    }

    private String normalize(String s) {
        return s.toLowerCase()
                .replaceAll("[\\u200B-\\u200D\\uFEFF]", "")  // 去零宽
                .replaceAll("[\\s\\p{Punct}]", "");            // 去分隔符（变形词兜底）
    }
}

A4. 微信内容安全调用（security.msgSecCheck v2）

// 评论提交服务：本地词库 -> 微信审核 -> 落库
public ReviewVO submitReview(ReviewReq req, Long userId) {
    rateLimiter.check("rate:comment:" + userId, 5, 60); // 用户维度限流
    // 1) 本地敏感词
    MatchResult local = sensitiveWordFilter.match(req.getContent());
    if (local.hasLevel1()) {
        auditLogService.log(req, 1, local.getHitWord(), 2, 0);
        throw new BizException(20003, "内容包含违规信息，请修改后再提交");
    }
    // 2) 微信审核
    MsgSecCheckResp wx = wechatClient.msgSecCheck(
        req.getContent(), userId, "food:" + req.getTargetId());
    int auditStatus;
    if (wx.isPass()) auditStatus = 1;
    else if (wx.isRisky()) auditStatus = 3; // 人工复审
    else { // revoke
        auditLogService.log(req, 2, null, 2, 0);
        throw new BizException(20003, "内容需修改后重新提交");
    }
    // 3) 落库 + 刷新评分（事务）
    Review review = reviewService.insert(req, userId, auditStatus);
    if (auditStatus == 1) dishStatService.refresh(req.getTargetId()); // 评分聚合
    auditLogService.log(req, 2, null, wx.getRiskLevel(), 1);
    return ReviewVO.of(review);
}

附录 B：排行榜热度聚合 SQL（定时任务每 10 分钟执行）

SELECT d.id        AS dish_id,
       d.name      AS dish_name,
       s.name      AS site_name,
       st.name     AS stall_name,
       d.avg_rating,
       COUNT(r.id)                       AS recent_cnt,
       ROUND(COUNT(r.id)*2 + AVG(r.rating)*10, 2) AS hot_score
FROM review r
JOIN dish d  ON d.id = r.target_id
JOIN stall st ON st.id = d.stall_id
JOIN site s  ON s.id = st.site_id
WHERE r.module = 'food'
  AND r.target_type = 'dish'
  AND r.audit_status = 1
  AND r.is_deleted = 0
  AND r.created_at >= DATE_SUB(NOW(), INTERVAL 7 DAY)
  AND d.status = 1 AND d.is_available = 1
GROUP BY d.id, d.name, s.name, st.name, d.avg_rating
ORDER BY hot_score DESC
LIMIT 20;
说明：近 3 天评论的时间衰减加权（x1.5）在应用层对结果二次计算后写入
Redis ZSET（rank:hot:dish:7 / rank:hot:dish:30），接口只读缓存零延迟；
菜品归属链为 dish -> stall -> site，榜单展示可溯源到食堂/校外区域名称。
