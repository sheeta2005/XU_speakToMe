# 第三批：举报与运营管理

交付日期：2026-10-16。分支：`codex/moderation-2026-10-16`，在已推送的第二批提交 `6a434ea` 上继续开发，包含前两批代码。新增业务注释标注“10/16”。本说明记录代码和自动化验证结果，不代表已部署或完成真机验收。

## 使用入口

- 普通用户：美食 → 菜品详情 → 他人已公开点评下的“举报”。选择垃圾广告、色情、辱骂、政治敏感、学术不端或其他原因，选填最多 200 字的说明后提交。本人点评使用删除入口，待复审点评不显示举报按钮。
- 管理员：我的 → 管理工作台。入口取自最新资料中的 `role=1`，管理页面每次进入重新核验角色；所有后台接口另行校验角色和账号状态，普通用户或封禁管理员无法操作。
- 管理员账号沿用既有用户角色，不增加自助提权或管理员注册入口。需由已有运维权限配置账号角色。

## 已完成的操作

| 页面 | 可执行操作 | 状态及失败处理 |
|---|---|---|
| 菜品详情 | 选择原因、填写说明、提交举报 | 提交中防重复，失败保留输入；同一用户对同一点评 24 小时去重；只接受未删除且已公开的美食点评 |
| 管理工作台·举报 | 按待处理、已下架处理、已驳回分页；查看原因、原文和评论当前状态；填写处理说明并下架或驳回 | 处理前确认；成功刷新分组；失败保留说明；已处理工单不可覆盖；原文读取失败可重试 |
| 管理工作台·复审 | 按待复审、已通过、已拦截分页；通过、拦截、下架、恢复 | 通过和拦截均重算菜品评分；已删除点评不能恢复；待复审原文仅作者可见，管理员从专用接口核实 |
| 对象维护 | 校区、地点、档口、菜品新增及编辑；按层级名称选归属；启用或停用 | 列表包含停用对象；校验名称、归属、排序和价格；失败保留草稿；价格可清空；评分及时间字段不接收客户端改写 |
| 敏感词库 | 新增、编辑词条和分类、调整直接拦截/人工复审等级、停用及恢复 | 校验字数、分类、等级和重复；保存后重载当前实例词库，对后续内容生效；原词和文本按同一规则归一化 |

对象启停保持原有含义：只修改当前对象，不自动级联修改下级状态，不删除历史点评或重写榜单。词库修改不自动重新审核历史点评，历史状态由人工复审调整。

## 接口调整

接口前缀均为 `/api/v1`，统一返回既有 `code/msg/data` 格式，写入身份来自登录上下文。管理分页 `page>=1`、`1<=size<=50`，列表使用 ID 作为同时间记录的排序补充。

| 接口 | 本批变化 |
|---|---|
| `POST /reports` | 校验说明长度、评论可举报状态，事务内累加举报次数并写入工单；写入失败释放本次 Redis 去重标记，允许重试 |
| `GET /admin/reports` | 校验分页和状态，状态为 0 待处理、1 已处理、2 已驳回 |
| `POST /admin/reports/{id}/handle` | `action=block/dismiss`，`handleResult` 最多 200 字；条件更新只处理待处理工单，驳回正确落为状态 2；下架、工单和评分使用同一数据库事务 |
| `GET /admin/reviews` | `auditStatus=3/1/2`，只列未删除的美食菜品点评；支持复审、公开和拦截分组 |
| `GET /admin/reviews/{id}` | 新增，管理员按需查看举报关联评论原文及删除/审核状态 |
| `POST /admin/audit/{id}/confirm` | 复用 `action=pass/block` 完成复审、下架和恢复；锁定评论后变更状态并重算评分，拒绝恢复已删除记录 |
| `GET /admin/campuses`、`/admin/sites`、`/admin/stalls`、`/admin/dishes` | 新增管理分页查询，包含停用对象 |
| `GET /admin/object-options` | 新增校区、地点、档口名称与父级关系选项，包含停用标记，供归属选择使用 |
| 既有对象 `POST`、`PUT /admin/{类型}/{id}` | 补齐归属、状态、文本长度、排序和价格校验，新增时可选择停用；屏蔽客户端提交的评分、创建时间等非维护字段 |
| `PUT /admin/sensitive-words/{id}` | 新增，提交完整词条、分类、等级及启停状态；修改后立即重载当前实例词库 |

对象修改页提交完整维护表单。菜品价格允许空值；其他文本空值作为空字符串保存。词库的 `category` 为 1 政治、2 色情、3 辱骂、4 广告、5 学术不端、6 其他，和举报原因的编号顺序不同，页面已分别映射。

## 待真实环境验收

以下步骤是待执行清单，本批没有把它们记为已通过：

1. 配置真实服务后，以普通用户及管理员分别登录；核验“我的”入口、直达管理页面的权限、主题和各页面布局。
2. 用户甲发布点评，用户乙举报并立即重复提交；核对第一次成功、第二次去重提示，说明草稿保留。
3. 管理员打开待处理工单，核对原因和原文；下架后普通用户刷新菜品详情，确认评论消失、评分与人数变化；重复处理旧工单应被拒绝。
4. 对另一工单执行驳回，核对已驳回分组和处理说明；原评论保持公开。作者已删除时，后台应显示删除状态，不能通过复审恢复。
5. 准备待复审点评；作者可见，其他普通账号不可见；管理员通过后公开，拦截后隐藏。对已拦截点评恢复时重新核对评分人数及均分。
6. 依次创建校区、地点、档口和菜品；验证归属选项、启停与恢复、价格留空及修改，确认历史点评不受删除影响。
7. 新增敏感词后提交命中内容，分别验证直接拦截与人工复审；修改、停用、恢复后再次提交，核对新内容按最新词库处理。
8. 检查真实 Redis 去重 TTL、每分钟限流、断网重试、分页、并发处理，以及开发者工具和真机的选择器与滚动定位行为。

本批未进行真实 MySQL/Redis/微信联调，也未在微信开发者工具或真机执行页面。测试直接注入用户上下文，不覆盖登录拦截器、真实会话及限流切面的集成。管理页面没有独立 Web 站点，随小程序提供；没有新增举报处理结果的订阅通知或个人工单查询页。

敏感词热更新目前作用于单个应用实例；多实例同步、对象选项随数据量增长的分页选择、并发评分缓存一致性和人工操作日志留存需在上线前继续验证或完善。工单保存处理人、处理时间及说明，评论保留当前审核结论；本批没有新增独立的完整操作历史表。
